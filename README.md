# 途电驿站 · 电动车出租店出租管理系统

单店电动车租赁门店的一体化管理系统。把「车在哪、谁在租、钱多少、什么时候该保养」这四件事从纸质台账里搬进系统：
员工端管车、开单、收款、结算、出报表；顾客端自己选车、下单、支付、查订单。

一条业务闭环贯穿全系统：

```
车辆档案 → 开单（原子占车）→ 支付（三通道）→ 归还验收 → 结算（退押金）→ 报表对账
```

- **单仓库双端**：一套 React 工程按登录角色分流员工端与顾客端，不维护两个前端。
- **零中间件**：不依赖 Redis、消息队列，会话共享与定时任务选主直接用 MySQL 完成，一台 2 核 4G 云主机即可上线。
- **并发正确性下沉数据库**：行级悲观锁 + 条件原子更新 + 乐观并发令牌 + 唯一键/CHECK 约束五层兜底，不靠进程内内存状态。
- **与课程文档严格对齐**：17 张表 / 134 个字段、21 个实体类、16 个控制器 / 119 个接口，均可在三份文档中找到出处。

## 角色与权限

| 角色 | 说明 | 可见范围 |
|---|---|---|
| 管理员 | 门店负责人，全部权限 | `/staff` 全模块，含用户、字典、日志、备份 |
| 前台 | 接待与开单 | 车辆、订单、结算、客户、会员、支付；无报表与系统配置 |
| 财务 | 资金与账目 | 支付、结算复核、报表；无车辆与用户管理 |
| 顾客 | 线上自助 | 独立路由，按 `customerId` 隔离数据 |

- 鉴权为 **JWT + 12 档具名授权策略**，接口未标注授权时由全局过滤器**默认拒绝**（fail-closed），新增接口忘加权限也不会裸奔。
- 同一账号只允许一处在线（单点登录）。被顶下线与账号停用都在 401 文案中区分，避免用户误以为是密码错。
- 密码 BCrypt 存储，登录失败计数达阈值后锁定，解锁由管理员操作。

## 快速开始

**前置**：.NET 10 SDK、Node 18+、MySQL 8.4+。

```bash
# 1) 建库并导入结构与种子数据（只需一次）
mysql -uroot -p < database/schema.sql
mysql -uroot -p < database/seed.sql

# 2) 本地配置：从模板复制后填本机口令
cp back/appsettings.Development.example.json back/appsettings.Development.json

# 3) 起后端（Swagger 在 /swagger）
cd back && dotnet run            # http://localhost:5105

# 4) 起前端
cd front && npm install
cd front && npm run dev          # http://localhost:5173
```

Windows 下直接双击 `start.bat`；`start.bat lan` 开启局域网模式（手机连同一 Wi-Fi 即可访问）。

**默认账号**：管理员 `trq / 123456`（首次启动自动创建，请立即改密）。前台、财务账号由管理员在「用户管理」创建，顾客在前端自行注册。

提交前的自检命令（与 CI 完全一致）：

```bash
dotnet build eRentalSystem.slnx -c Release -warnaserror   # 0 警告 0 错误
cd front && npm run build                                 # tsc 类型检查 + vite 构建
```

> `appsettings.json` 刻意留空，`appsettings.Development.json` 已被 `.gitignore` 排除，真实口令不进版本库。
> 生产环境用环境变量注入，见[部署](#部署)。

## 系统架构

```
浏览器（React SPA · 员工端 / 顾客端）
        │  HTTPS
        ▼
nginx（TLS 1.3、静态资源、反向代理、fail2ban 兜底）
        │  127.0.0.1:5105
        ▼
ASP.NET Core
  ├─ 中间件：全局异常脱敏 → 单点登录校验 → 限流 → 审计日志
  ├─ 授权：JWT 验签 → 12 档具名策略（fail-closed）
  ├─ 控制器（16 个 / 119 个接口，按业务域划分）
  └─ 服务层（订单、结算、支付三通道、车辆闸门、并发工具、备份恢复…）
        │  EF Core
        ▼
MySQL 9.6（17 张表，InnoDB 行锁 + 唯一索引 + CHECK 约束）
```

**不依赖进程内状态**：登录会话登记在 `system_config`（多实例共享，单点登录全局生效）；每日备份、超时订单回收启动前先抢 MySQL 命名锁 `GET_LOCK`，抢不到就认定别的实例在做，直接让位。因此**双机部署不需要任何额外组件**，也不会出现「同账号互踢失效」「备份跑两遍」。

## 并发与一致性设计

门店里同一张订单被两个窗口同时操作是常态：前台 A 点「归还结算」的同时前台 B 也在点；顾客在自助端连点取消；
支付宝的异步通知因网络重试重复推送同一条消息。如果代码只写「先查状态、再写状态」，两个请求都会读到同一份旧状态，
于是各生成一条结算单、各退一次押金——账面上看不出异常，钱已经多退了。

系统的并发控制全部下沉到数据库，分五层：

| 层 | 手段 | 实现位置 |
|---|---|---|
| ① 行级悲观锁 | 结算、续租、退款、支付入账等「读—判定—写」跨字段流程，先 `SELECT … FOR UPDATE` 锁行，并发请求在库内排队，拿到锁后**`Reload` 重读**再判定 | `Services/DbRowLock.cs` |
| ② 条件原子更新 | 车辆占用（空闲→在租）、维保/报废迁移、工单完工压成一条 `UPDATE … WHERE status=?`，判定与写入不可分割；超时单回收用 `FOR UPDATE SKIP LOCKED` 分批，多实例各处理各的、不重复取消 | `OrderService`、`VehicleLeaseGuard`、`MaintenanceService` |
| ③ 乐观并发令牌 | `Vehicle.VehicleStatus`、`RentalOrder.OrderStatus` 标 `[ConcurrencyCheck]`，EF 生成的 UPDATE 会带 `AND status=@原值`，被抢先修改时失败而不是静默覆盖裸 SQL 写入的新状态。**不加 version 列**，不破坏 17 表 / 134 字段 | `Models/Vehicle.cs`、`Models/RentalOrder.cs` |
| ④ 数据库约束 | `uk_settle_order` 唯一索引 + 8 条业务唯一键（账号、身份证、车牌、订单号、工单号、配置键、盘点单号、报表号）+ 5 条 CHECK + 4 条复合索引 | `Data/DbInitializer.cs`、`database/schema.sql` |
| ⑤ 冲突分类处理 | 1213 死锁（事务已被 InnoDB 回滚，重放有效）→ 整段重放最多 3 次；1205 等锁超时（持锁者还在跑，重放必然再超时）→ **不重试**，5 秒直接返回中文提示 | `Services/DbConcurrency.cs` |

两个工程细节：

- 所有业务事务使用 `READ COMMITTED` 隔离级别，只锁命中行、不加间隙锁，避免结算与下单并发时互相咬死。
- 每个事务开始先把会话级 `innodb_lock_wait_timeout` 压到 **5 秒**，拿不到锁立即返回可读提示，不让请求线程挂满默认的 50 秒。

定时任务的选主用 MySQL 命名锁（`GET_LOCK`）。它的生命周期绑在**物理连接**上，而连接池的「关闭」只是把连接还回池里、TCP 并不断开——所以释放路径做了三重加固：连接关了就重新打开再释放、循环释放到持有计数归零、释放后用 `IS_USED_LOCK` 回读校验，仍被持有就清除池中的物理连接交由 MySQL 兜底回收（`Services/DbLockService.cs`）。

**实测结果**（真实 HTTP 接口并发打，非单元模拟）：

| 场景 | 结果 |
|---|---|
| 6 个并发请求下单同一辆车 | 1 单成功，5 单收到「刚被他人租走」 |
| 6 个并发请求结算同一张已支付订单 | 数据库仅 1 条结算记录、1 次退款；其余 5 个在 **0.16 秒**内被拒 |
| 4 个并发请求各续租 6 小时 | 到期时间精确 +24 小时，无丢失更新 |
| 3 个并发请求各退同一笔的 60% | 仅 1 笔成功，另两笔读到已更新的可退余额 |
| 6 个并发支付通知到达同一待支付订单 | 仅首次入账，其余命中幂等分支，`payment_record` 始终 1 条 |
| 行锁被他人占用 32 秒 | **5.15 秒**返回「该单据正在被其他同事处理」，不再等满 15 秒后被前端超时打断 |
| 直接向库里插重复车牌 / 重复账号 / 重复配置键 | 全部被 1062 拒绝 |

以上手段**未新增任何业务表或字段**：行锁作用于既有主键与索引，唯一键、CHECK 与并发令牌都是表级/列级约束，17 表 / 134 字段的映射关系不变。

## 支付与退款

### 三级降级

| 通道 | 状态 | 降级路径 |
|---|---|---|
| 支付宝 | 真实对接（RSA2） | 凭证齐全走官方收银台 → 缺凭证降级沙箱 → 再缺降级内置模拟收银台 |
| 微信支付 | APIv3 已实现（H5 下单 / 查单 / 回调解密 / 退款） | 无商户凭证时走模拟 |
| 银行卡 | 通用收银网关协议已实现（下单 / 回调验签 / 退款） | 同上 |

入账只认**验签或解密通过的数据**：支付宝异步通知（生产主路）与主动查单（`alipay.trade.query`，本地收不到 notify 时的唯一同步手段）共用同一段幂等 + 金额校验逻辑。模拟收银台走独立端点 `/api/payment/mock/notify`，要求 `trade_type=MOCK` 且生产模式直接拒绝，绝不放宽真实回调的验签。

### 退款幂等

`PaymentService.Refund` 按通道能力分流，返回值明确区分「真的退了钱」与「只记了账」。三通道共用一个幂等键：

```
{payId}R{累计应退金额的分}
```

同一笔支付、同一个累计退款额只对应一个请求号，**网关成功但本地事务回滚后重试不会重复退款**。余额不足、退超（`> pay_amount - refund_amount`）、未支付单直接拒绝。归还结算在事务内直接发起退款，退款失败则整笔结算回滚，杜绝「订单已完结、押金没退」。模拟模式下只记账，接口文案明确写「未发生资金划转，请线下退还」。

## 数据模型

17 张表覆盖门店全流程：

| 分类 | 表 |
|---|---|
| 权限与用户 | `role`、`permission`、`system_user`（TPH 判别列 `user_type`：admin / reception / finance）、`customer` |
| 车辆资产 | `vehicle`、`maintenance_order`、`scrap_record`、`car_check_list`、`check_report` |
| 租赁与资金 | `rental_order`、`renewal_record`、`payment_record`、`settle_record`、`member_rights` |
| 系统支撑 | `system_config`、`system_log`、`message`（通用消息表：顾客事件通知 + 工作人员预警，含已读状态） |

字段名、类型、长度与《唐荣强 .docx》图 4-1 ~ 图 4-17 逐项一致。单点登录、数据字典、通知消息均复用现有表，不额外建表。
实体类 22 个而库表 17 张，差额来自 TPH 继承——`AdminUser` / `ReceptionUser` / `FinanceUser` 共用一张 `system_user`。

表级约束由 `DbInitializer` 在启动时**幂等补建**（已存在则跳过，重复启动不报错），老库升级无需手工执行 DDL。
补建范围包括 8 条业务唯一键（账号、身份证、车牌、订单号、工单号、配置键、盘点单号、报表号）与 4 条复合索引——
这些在 `schema.sql` 里有声明，但用 EF `EnsureCreated` 建库时不会落地（模型未配 `HasIndex`），
所以必须由代码补，否则「同一车牌能建两辆」「同一配置键能插两条」这类问题只在手工导库的环境里不出现。
建唯一键前先探测存量重复，有重复只打印并跳过，不阻断启动。

## 部署

完整步骤见 `服务器部署/部署说明.txt`。要点：

```bash
# 生产配置全部走环境变量，不写入仓库
export Jwt__Key="$(openssl rand -base64 48)"
export ConnectionStrings__DefaultConnection='Server=127.0.0.1;Database=erental;User=erental_app;Password=<强密码>;CharSet=utf8mb4;'
dotnet publish -c Release -o publish

cd front && npm run build
```

- 生产配置放 `/etc/erental/erental.env`（systemd `EnvironmentFile=`），发布时 `scp -r publish/*` 覆盖代码目录也不会冲掉配置。
- Kestrel 只监听 `127.0.0.1:5105`，由 nginx 443 反代，HTTP 强制 301 跳 HTTPS。
- **JWT 密钥不写死**：按 `Jwt__Key` → `App_Data/signing.key` → 首次启动随机生成 48 字节并落盘（权限 600）的顺序取用。仓库里没有任何可用的默认密钥，本地开箱即用，也不会出现「线上跑着和仓库里一样的密钥」。多机部署需显式填同一把，否则各签各的、互不认。
- 连接串为空时后端**拒绝启动**，避免连错库却毫无提示。
- `Backup__Key` 单独保管，换密钥会导致旧备份无法解开。未配置时备份密钥由 JWT 密钥派生，而 JWT 密钥现在是每台机器随机生成的——**跨机器恢复备份必须显式配置 `Backup__Key`**。

## 已知边界

1. **微信 / 银行卡未经真实商户凭证验证**：协议实现完整（下单、查单、回调验签、退款），但只在模拟通道跑通过；真实资金链路需商户号与证书就位后再回归一次。模拟通道仅记账，不发生资金划转。
2. **多实例依赖同一数据库**：会话与定时任务选主都落在 MySQL 上，多实例必须共用同一个库；若将来跨机房部署，需换成 Redis 或外部调度。
3. **硬件对接程度**：扫码枪 ✓（键盘仿真 + 摄像头扫码）；小票为浏览器打印（非 ESC/POS，热敏机需装驱动）；身份证读卡器无专用适配（HID 键盘可直接输入）；钱箱未接。
4. **数据规模假设**：单店（千级车辆、十万级订单）。服务端分页与报表 `GROUP BY` 已就位，但报表仍为实时聚合、未做预计算宽表；百万级订单建议加日汇总表。
5. **i18n 未做**：界面与文档均为中文硬编码。
6. **结算事务内含网关调用**：支付宝真实通道退款在结算事务内发起，持锁时间等于网关往返（几百毫秒到十几秒）。
   门店并发极低时可接受；若将来并发上来，应改为「先落退款中状态、提交后调网关、失败补偿」。
7. **一单只能结算一次**：`uk_settle_order` 永久禁止同一订单生成第二条结算记录。
   需要调账时目前只能由财务走线下冲正，系统内没有红冲单功能。
